# x402 PayPal

Pay-per-request premium API for autonomous agents, settled with a PayPal Vault token.
The agent pays once for access. The funding source is a saved PayPal wallet or a saved card.
No card data reaches the API server.

Open the single link and press **Run a live $1 payment** — no install, no sign-in, no terminal:

**https://g4s46q34fmmfy3alacn7z7zdli.srv.us/**

The page creates a fresh judge session on load:

- a new agent with a `$10.00` sandbox budget,
- a pre-provisioned, tokenized PayPal sandbox card (`VISA •••• 1111`),
- one click runs a real x402 `402 → 200` round trip and a real PayPal sandbox capture,
- **Send identical signature** replays the exact `PAYMENT-SIGNATURE` and returns
  `X-X402-Replay: true` with no second charge and no budget change.

Everything visible in the transaction theater is returned by the running Spring Boot
service. Failures are shown as failures. The premium data is canned and the card is a
PayPal sandbox test card, so no real money moves.

### Optional: walk through card setup

The judge session already has an active card, so nothing needs to be set up. The
**Funding source** panel says **Card already enrolled** and shows the active
`VISA •••• 1111`. To try the PayPal CardFields flow anyway:

1. Open **Card setup** or choose **Set up a different card** in the Funding source panel.
2. Press **Start optional card setup**. A hosted page opens at `/enroll/{token}` with
   PayPal's CardFields.
3. Use the sandbox test card `4111 1111 1111 1111`, any future expiry, and any CVV.
4. Return to the judge page. It polls the enrollment and switches to the new card once
   PayPal confirms it; the next paid run uses the new vault token.

The card already enrolled stays active while an optional setup is pending. Card numbers
go directly to PayPal; this service stores only an encrypted vault token.

### Run the judge demo locally

```dotenv
DEMO_ENABLED=true
DEMO_VAULT_TOKEN=<payment token from a sandbox card enrollment>
DEMO_CARD_BRAND=VISA
DEMO_CARD_LAST4=1111
DEMO_BUDGET_CENTS=1000
DEMO_MAX_SESSIONS_PER_HOUR=300
```

`DEMO_VAULT_TOKEN` is the PayPal Vault payment token that the app stores after a
CardFields enrollment. The demo endpoint uses it read-only to create a fresh, active
enrollment for each page visit:

```bash
curl -sS -X POST http://localhost:8080/v1/demo/session
```

`GET /v1/demo/info` reports whether the demo is configured. Both endpoints are only
active while `DEMO_ENABLED=true` and `DEMO_VAULT_TOKEN` is set; create sessions are
rate-limited per client address.

## Deploy the single link

The app serves both the API and the judge page, so a single container is enough:

```bash
docker build -t x402-paypal .
docker run --env-file .env -p 8080:8080 x402-paypal
```

On a container host, set the same `.env` values plus `APP_PUBLIC_BASE_URL` to the
public URL. `server.forward-headers-strategy` is enabled, so x402 challenge URLs use
the public host even behind a proxy or tunnel. `server.port` honors `$PORT` for hosts
such as Render. `render.yaml` contains a ready blueprint with the demo environment
variables.

### Deploy on Render

1. Push this repository to GitHub.
2. In Render, choose **New → Blueprint** and select the repo. Render reads
   `render.yaml` and creates a Docker web service named `x402-paypal-judge-demo`.
3. Fill the secrets marked `sync: false` when prompted:

   | Variable | Value |
   | --- | --- |
   | `PAYPAL_CLIENT_ID` | your sandbox client ID |
   | `PAYPAL_CLIENT_SECRET` | your sandbox secret |
   | `DEMO_VAULT_TOKEN` | the PayPal Vault payment token from `.env` |
   | `PAYPAL_WEBHOOK_ID` | optional; only needed if you use webhooks |

   `X402_MASTER_KEY` and `X402_VAULT_KEY` are generated by Render automatically.
4. After the first successful deploy, copy the service URL and set
   `APP_PUBLIC_BASE_URL` to it (for example `https://x402-paypal-judge-demo.onrender.com`),
   then redeploy. Request-derived URLs already work, but this keeps generated links
   explicit.
5. Open the service URL and press **Run a live $1 payment**.

Two Render behaviours worth knowing:

- **Free plan sleeps after 15 minutes idle**, so the first visit can take ~50 seconds
  to wake. For a judged demo window, use `plan: starter`, or ping
  `/actuator/health` every few minutes.
- The container filesystem is **ephemeral**. `render.yaml` therefore sets H2 to
  in-memory and disables the H2 console. Judge sessions are created per page load, so
  nothing needs to persist.

For a quick local share without an account, srv.us issues a stable HTTPS URL derived
from your SSH key:

```bash
ssh-keygen -t ed25519            # once, if you have no key
ssh -R 1:localhost:8080 srv.us   # prints https://<stable-id>.srv.us/
```

`localhost.run` also works, but free hostnames rotate on reconnect:

```bash
ssh -R 80:localhost:8080 nokey@localhost.run
```

## What is implemented

- Agent bootstrap with API key and derived HMAC secret.
- x402 v2 `402 Payment Required` with a base64 `PAYMENT-REQUIRED` header.
- HMAC-signed payment payloads with challenge, nonce, expiry, amount, asset, and resource checks.
- Budget reservation, replay detection, and cached content replay.
- Wallet enrollment with a PayPal approve URL.
- Card enrollment with PayPal CardFields hosted on `/enroll/{token}`.
- Per-request PayPal order create and capture using the saved vault token.
- SCA / payer-action mapping and a resume endpoint.
- PayPal webhook verification, dedupe, capture reconcile, and vault-token disable.
- Demo agent CLI.

Prices: `/v1/premium/quote` = `$1.00`, `/v1/premium/report` = `$2.00`. Both are configurable.

## Requirements

- Java 21.
- A PayPal sandbox business account with Accept Payments, Vault, and Advanced Credit/Debit Card Payments enabled.
- Sandbox client ID and secret.

`PAYPAL_MERCHANT_ID` is not required for a standalone seller integration.

Generate the two x402 keys with:

## Create an agent

```bash
curl -sS -X POST http://localhost:8080/v1/agents \
  -H 'Content-Type: application/json' \
  -d '{"name":"demo-agent","budgetCents":1000}'
```

The response contains `agentId`, `apiKey`, and `hmacSecret`.
The API key is shown once; the server stores only its hash.
The HMAC secret is derived from `X402_MASTER_KEY`, so the server can recompute it.

## Enroll a payment method

Wallet:

```bash
curl -sS -X POST http://localhost:8080/v1/enrollments \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"sourceType":"PAYPAL_WALLET"}'
```

Open `approveUrl` and approve with a sandbox buyer. The return URL exchanges the approved setup token automatically.
If the return URL cannot reach `localhost`, call exchange after approval:

```bash
curl -sS -X POST http://localhost:8080/v1/enrollments/$ENROLLMENT_ID/exchange \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{}'
```

Then check the enrollment:

```bash
curl -sS http://localhost:8080/v1/enrollments \
  -H "Authorization: Bearer $API_KEY"
```

Card:

```bash
curl -sS -X POST http://localhost:8080/v1/enrollments \
  -H "Authorization: Bearer $API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"sourceType":"CARD"}'
```

Open `enrollmentUrl` in a browser and pay with a PayPal sandbox test card.
CardFields creates the vault setup token and posts it to the server.
No PAN reaches this service.

## Make a paid request

Without a payment header, the API returns `402` and a `PAYMENT-REQUIRED` header:

```bash
curl -i http://localhost:8080/v1/premium/quote \
  -H "Authorization: Bearer $API_KEY"
```

The demo agent does the full flow: reads the header, signs the challenge, retries, and prints the receipt.

```bash
./gradlew demoAgent --args="--base-url http://localhost:8080 \
  --api-key $API_KEY --hmac-secret $HMAC_SECRET --agent-id $AGENT_ID"
```

Use `--path /v1/premium/report` for the `$2.00` endpoint.
Use `--wait` to pause after `PAYER_ACTION_REQUIRED`, approve in the browser, then resume.

Replay the same `PAYMENT-SIGNATURE` to get the same content with `X-X402-Replay: true` and no second charge.

## API

| Method | Path | Auth | Purpose |
|---|---|---|---|
| `POST` | `/v1/agents` | none | Demo bootstrap |
| `GET` | `/v1/agents/me` | API key | Agent budget and status |
| `POST` | `/v1/enrollments` | API key | Create wallet or card enrollment |
| `GET` | `/v1/enrollments` | API key | List enrollments |
| `GET` | `/v1/enrollments/{id}` | API key | Enrollment status |
| `POST` | `/v1/enrollments/{id}/exchange` | API key | Exchange an approved setup token |
| `DELETE` | `/v1/enrollments/{id}` | API key | Revoke and delete the vault token |
| `GET` | `/enroll/{token}` | signed link | Hosted card page |
| `GET` | `/enroll/{token}/return` | signed link | Wallet or 3DS return |
| `GET` | `/v1/premium/health` | API key | Free health check |
| `GET` | `/v1/premium/quote` | x402 | `$1.00` quote |
| `GET` | `/v1/premium/report` | x402 | `$2.00` report |
| `GET` | `/v1/payments/attempts/{id}` | API key | Payment attempt status |
| `POST` | `/v1/payments/attempts/{id}/resume` | API key | Resume after payer action |
| `POST` | `/webhooks/paypal` | PayPal signature | Capture and vault events |

## Error codes

`402` responses use `PAYMENT_SIGNATURE_REQUIRED`, `INVALID_SIGNATURE`, `PAYMENT_MISMATCH`,
`CHALLENGE_EXPIRED`, `REPLAY_DETECTED`, `ENROLLMENT_REQUIRED`, `BUDGET_EXCEEDED`,
`PAYER_ACTION_REQUIRED`, `INSTRUMENT_DECLINED`, or `PAYMENT_FAILED`.
A settled replay returns `200` plus `X-X402-Replay: true`.

## Security model

- The agent authenticates with an API key and signs the x402 challenge with its derived HMAC secret.
- The vault token never leaves the server and is encrypted at rest with AES-GCM.
- The vault token is a bearer charge credential. It is not placed in the x402 header.
- Card data goes from the browser to PayPal. The server sees only the setup token and the vault token.
- Set `PAYPAL_WEBHOOK_ID` to verify webhook signatures. If it is empty, local webhook verification is skipped.
- API keys are high-entropy random values. The server stores a SHA-256 hash, not the key.
